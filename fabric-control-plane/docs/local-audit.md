# Implementation audit — updated 2026-10-17

Repeat-verification correction: upstream `externalchaincode sync` forces `imagePullPolicy: Always` when updating an existing service. That cannot pull a local-only development image. The worker now validates and adopts the existing package/image and enforces `Never`, then checks rollout and TLS before invoking Fabric. An early repeat test required a live policy correction; subsequent qualification must use the rebuilt worker without manual resource changes.

Final verification: the rebuilt worker passed another browser-driven transaction check without manual Kubernetes mutation, in 16.5 seconds. Both peers reached matching height 11. The final API restart preserved the real operation/snapshot in PostgreSQL and current workload health returned ready. See [commands, results and retained network](local-acceptance-results.md).

Working: separate React and Go repositories; six consistently styled wizard screens; typed/validated desired JSON with cloud and cluster intent; revision-aware draft persistence; deterministic Bevel candidate compilation; optional Okta and PostgreSQL draft repositories; real Fabric CA/Docker development profile with three Raft orderers, two peers, channel membership and a Go chaincode write/query.

Completed during local qualification: a real kind/Bevel worker, Ansible/Helm bootstrap, PostgreSQL deployment journals/snapshots, API deployment/status/health/log/retry/cleanup endpoints and the six-step Kubernetes console flow. A browser test interrupted its own worker, retried, committed a real Go chaincode transaction and queried it from both peer organizations, checked equal ledger heights/hashes, checked three active orderers and two TLS CAs, reloaded the dashboard, and detected/restored a stopped peer. A second browser test resumed the saved deployment, verified another real transaction, read node logs, cancelled the delete confirmation and then completed owned-network cleanup. Details and commands: [local Kubernetes](local-kubernetes.md).

Still unavailable: cloud candidates remain suspended and no AWS/EKS execution adapter is qualified. No AWS/EKS target or credentials are configured. Native arbitrary-topology execution remains future work. Enterprise authentication exists as optional Okta integration but has no live tenant qualification. The local worker uses development-only cluster-admin privileges, a single-node cluster and a single-process PostgreSQL-backed executor; it is not a B2B production deployment. Deployment tables use application tenant scoping, while draft tables additionally enforce PostgreSQL RLS. Distributed queue leasing, tenant workload RBAC, production secret management, HA, metrics, backup/restore and certificate rotation need separate production qualification.

Broken assumptions: successful JSON export, tool installation, Ansible syntax checks or Kubernetes pod readiness cannot prove a Fabric network is usable. The old fork cannot be qualified by replacing version strings. Mock success must not be promoted into verified infrastructure. Current Docker engine memory is approximately 5.8 GiB, so the local test profile must stay small and resource pressure must be checked.

Corrections found by actual execution: stale upstream chart CRDs, legacy Helm CRD ownership, CLI singular resource names, NodePort-zero SDK endpoints, multi-organization commit endorsements, chaincode service port mismatch, retry root-file restoration and a chaincode-service readiness race. The worker now checks rollout and a validated TLS handshake before invoking chaincode; it also stops on enrollment Secret read errors instead of regenerating credentials. The bootstrap rejects legacy CRD-template ownership before upgrading. An early bootstrap iteration removed failed manual test resources while migrating CRDs; fresh acceptance resources were recreated and the corrected bootstrap was rerun successfully against a healthy network. No simulated result is counted as Fabric acceptance.

Preserved: working Docker development logic, revision validation, the reference repositories and separate React/Go repositories. AWS/Azure provisioning stays disabled. Tests of the older Docker-only profile are opt-in to avoid starting a second network during kind qualification.
